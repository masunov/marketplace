# API

## Создание заказа

### Описание изменений
Одна позиция – один код, даже если SKU повторяется в заказе.

Для обратной совместимости старая однопозиционная форма `{"sku":"KEY-GTA5"}` продолжает работать.

Оплата запрашивается автоматически при создании: заглушка ПС отвечает «принято», а итог
присылает вебхуком с задержкой. Вручную вебхук слать не нужно.

Автосписание выключается флагом `PS_MIR_AUTO_CHARGE=false`. Тогда заказ ведет себя как
на первом этапе — остается в `created`, пока вебхук не пришлют снаружи, и исход оплаты
задает отправитель, а не жребий заглушки. Флаг проверяется в том процессе, который создал
заказ, поэтому тестовые команды выключают его для своего прогона и шлют вебхуки сами.

Вебхук в этом случае шлется руками, тем же контрактом, что и у заглушки:

```bash
curl -X POST http://localhost:8585/api/payment_systems/ps_mir/callback \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{
    "event_id":   "evt_manual_001",
    "order_id":   "01a08aa5-e98b-72f7-8922-425c0645386f",
    "status":     "paid",
    "amount":     "1990.00",
    "currency":   "RUB",
    "created_at": "2026-09-10T09:30:00Z"
  }'
```

`status` принимает `paid` или `failed`, `amount` и `currency` обязаны совпасть с заказом —
иначе вебхук будет отмечен обработанным, но статус не сменится, и расхождение всплывет
в сверке как `amount_mismatch`. Повтор с тем же `event_id` отсекается по
`unique(ps_callback_id, payment_system)`.

#### Статусы заказа

Статус заказа выводится из статусов позиций, а не назначается напрямую. Заказ из нескольких
позиций может закончиться тремя разными способами, и все три — нормальный исход, а не сбой.

| Статус              | Конечный | Описание                                                                  |
|---------------------|----------|---------------------------------------------------------------------------|
| created             | нет      | Заказ создан, списание запрошено, ждем подтверждения от платежной системы |
| paid                | нет      | Оплата подтверждена, запускается выдача по каждой позиции                 |
| delivering          | нет      | Позиции выдаются, каждая своим темпом и своим поставщиком                 |
| delivered           | да       | Все позиции выданы, деньги остались у продавца                            |
| partially_delivered | да       | Часть позиций выдана, за остальные деньги вернулись                       |
| refunded            | да       | Не выдано ничего, деньги вернулись целиком                                |
| payment_failed      | да       | Оплата не прошла, выдача не запускалась                                   |

Статусы `out_of_stock` и `delivery_failed` на уровне заказа остались от первого этапа
и новым кодом не выставляются: теперь это исходы **позиции**, а не всего заказа. Значения
сохранены, чтобы заказы, созданные до второго этапа, продолжали читаться.

#### Статусы позиции

| Статус          | Выдача завершена | Конечный | Содержимое | Описание                                               |
|-----------------|------------------|----------|------------|--------------------------------------------------------|
| pending         | нет              | нет      | нет        | Позиция ждет оплаты заказа                             |
| delivering      | нет              | нет      | нет        | Идет получение кода у поставщика                       |
| delivered       | да               | да       | да         | Код получен, проверен и привязан к позиции             |
| out_of_stock    | да               | нет      | нет        | Кода нет ни у одного поставщика, позиция ждет возврата |
| delivery_failed | да               | нет      | нет        | Выдать не удалось, позиция ждет возврата               |
| refunded        | да               | да       | нет        | Деньги за позицию вернулись покупателю                 |

Различие между «выдача завершена» и «конечный» существенно. `out_of_stock` и `delivery_failed`
означают, что у поставщиков больше ничего не спрашиваем, но деньги еще не разнесены: такая
позиция ждет возврата и по нему переходит в `refunded`. Заказ закрывается, только когда все
позиции конечные, — до этого у него ненулевой `money.in_flight_total`.

`delivery_failed` отличается от `out_of_stock` тем, что кода нет не наверняка. Он ставится,
когда неопределенность не удалось разрешить: поставщик мог выдать код, но не подтвердил
этого. Такие позиции подбирает `marketplace:recover-orders` и сверка.

## Состояние заказа на прошлый момент

### Запрос
```bash
curl http://localhost:8585/api/orders/{id}?as_of=2026-09-09T11:55:55" -H 'Accept: application/json'
```

### Параметры запроса

| Параметр | Тип               | Обязателен | Описание                                                                                                 |
|----------|-------------------|------------|----------------------------------------------------------------------------------------------------------|
| as_of    | String (ISO-8601) | да         | Момент, на который восстанавливается состояние. Без него метод отдает обычный ответ с текущим состоянием |

Часовой пояс в `as_of` разбирается: `2026-09-09T11:55:55` трактуется как время приложения.

### Ответ
**HTTP 200**

```json
{
    "data": {
        "order_id": "01a0833c-238a-7232-b2f2-df098db15f60",
        "as_of": "2026-09-09T11:55:55+03:00",
        "status": "delivering",
        "items": [
            {
                "id": "01a0833c-238c-71c7-849c-83734b7e88c1",
                "price": "1200.00",
                "status": "delivering"
            },
            {
                "id": "01a0833c-238e-72bf-a111-a9511cf9b5f1",
                "price": "1290.00",
                "status": "delivered"
            }
        ],
        "money": {
            "charged_total": 2490,
            "refunded_total": 0,
            "held_total": 2490
        },
        "history_complete": true
    }
}
```

### Поля ответа

| Поле                 | Тип              | Обязателен | Описание                                                               |
|----------------------|------------------|------------|------------------------------------------------------------------------|
| order_id             | String (uuid v7) | да         | Идентификатор заказа                                                   |
| as_of                | String           | да         | Момент, на который восстановлено состояние, со смещением               |
| status               | String           | да         | Статус заказа на этот момент, из таблицы статусов заказа               |
| items                | Array            | да         | Позиции заказа                                                         |
| items[].id           | String (uuid v7) | да         | Идентификатор позиции                                                  |
| items[].price        | Decimal          | да         | Стоимость позиции                                                      |
| items[].status       | String           | да         | Статус позиции на этот момент, либо `unknown` — см. `history_complete` |
| money                | Object           | да         | Деньги, двинувшиеся к этому моменту                                    |
| money.charged_total  | Decimal          | да         | Списано к этому моменту                                                |
| money.refunded_total | Decimal          | да         | Возвращено к этому моменту                                             |
| money.held_total     | Decimal          | да         | Удерживалось: списано минус возвращено                                 |
| history_complete     | Boolean          | да         | Хватает ли истории, чтобы отвечать про статусы позиций                 |

Состав `money` отличается от обычного ответа намеренно. `delivered_total` и `settled` здесь
не отдаются: первое требует знать, какие позиции выданы **сейчас**, второе — завершен ли заказ,
а оба вопроса относятся к настоящему, а не к запрошенному моменту. На прошлый момент отвечают только три величины: сколько списали, сколько вернули и сколько удерживали.

### Про `history_complete`

Флаг отвечает на вопрос, можно ли доверять статусам позиций в этом ответе.

| Значение | Что означает                                                                    |
|----------|---------------------------------------------------------------------------------|
| `true`   | История полна, статусы позиций восстановлены по событиям                        |
| `false`  | Событий позиций нет, хотя заказ доходил до выдачи. Статусы отданы как `unknown` |

Так выглядят заказы первого этапа: тогда статусы позиций не записывались, писались только
статусы заказа.

Статусы заказа и суммы при `history_complete: false` остаются верными: они восстанавливаются
из своих лент, которые велись с первого этапа.

**HTTP 404** если на указанный момент заказа еще не существовало

```json
    "error": "Order did not exist at that moment"
}
```

**HTTP 422** если `as_of` не разбирается как дата

## Итоги за период

### Запрос
```bash
curl "http://localhost:8585/api/reports?from=2026-09-09T00:00:00&to=2026-09-09T23:59:59" -H 'Accept: application/json'
```

### Параметры запроса

| Параметр | Тип               | Обязателен | Описание                                            |
|----------|-------------------|------------|-----------------------------------------------------|
| from     | String (ISO-8601) | да         | Начало отрезка, граница включается                  |
| to       | String (ISO-8601) | да         | Конец отрезка, граница включается, не раньше `from` |

Часовой пояс разбирается: `2026-09-09T00:00:00` трактуется как время приложения.

### Ответ
**HTTP 200**
```json
{
    "data": {
        "from": "2026-09-09T00:00:00+03:00",
        "to": "2026-09-09T23:59:59+03:00",
        "charged_total": 862140,
        "refunded_total": 292100,
        "net_total": 570040,
        "orders_touched": 390
    }
}
```

### Поля ответа

| Поле           | Тип     | Обязателен | Описание                                                |
|----------------|---------|------------|---------------------------------------------------------|
| from           | String  | да         | Начало отрезка, как его разобрали, со смещением         |
| to             | String  | да         | Конец отрезка, как его разобрали, со смещением          |
| charged_total  | Decimal | да         | Списано за период                                       |
| refunded_total | Decimal | да         | Возвращено за период                                    |
| net_total      | Decimal | да         | Сальдо: списано минус возвращено                        |
| orders_touched | Integer | да         | Сколько разных заказов дало хотя бы одно движение денег |

Отрезок берется по `processed_at` — «когда деньги двинулись», а не «когда мы записали
строку». Поэтому заказ, оплаченный вчера и возвращенный сегодня, попадет в оба отчета:
во вчерашний списанием, в сегодняшний возвратом. `net_total` — сальдо движений за период,
а не заработок по заказам, созданным в этом периоде.

В итоги входят только состоявшиеся движения. Отказ платежной системы в возврате лежит
в ленте, но денег не двигал и в `refunded_total` не попадает — такую позицию подбирает сверка.

`orders_touched` считает заказы, а не проводки: заказ, у которого в периоде и списание,
и возврат, посчитан один раз.

### Ошибки

**HTTP 422** если параметр отсутствует или не разбирается как дата

```json
{
    "message": "The from field is required.",
    "errors": {
        "from": ["The from field is required."]
    }
}
```

**HTTP 422** если `to` раньше `from`

```json
{
    "message": "The to field must be a date after or equal to from.",
    "errors": {
        "to": ["The to field must be a date after or equal to from."]
    }
}
```

## Состояние очередей

### Описание
Что происходит прямо сейчас: сколько позиций ждет выдачи, сколько уже выдано, сколько
осталось лимита у поставщиков и насколько глубоки очереди. Снимок на момент запроса,
параметров нет.

Позиции считаются по базе, глубины очередей — по Redis, и эти числа намеренно расходятся:

`group by`, а не заранее заданный набор ключей. Статусы позиции описаны в таблице выше,
в разделе о получении заказа.

Список очередей берется из конфига Horizon, а не задан в самом методе: разойдись эти два
списка, в отчете просто не было бы очереди, которую воркер при этом разбирает. Порядок тоже
конфиговый — Horizon читает очереди по списку, поэтому он же и есть приоритет, и первой идет
`created-orders-queue`, с которой начинается жизнь заказа: запрос списания в платежную систему.

### Про лимиты поставщиков

Окно — календарная минута, и `requests_this_minute` это тот же счетчик, который ограничивает
запросы, а не отдельная метрика рядом с ним. Поэтому отчет не может разойтись с механизмом,
но и `remaining_in_window` на стыке минут восстанавливается целиком, а не плавно.

`rpm_limit` отдается тот, что действует у воркеров прямо сейчас: сначала смотрится значение
в общем хранилище, и только если его нет — конфиг. Лимит, поднятый на лету, виден здесь сразу.

При `rpm_limit` равном нулю ограничения нет, и `remaining_in_window` отдается как
`9223372036854775807` — «сколько угодно».

### Про `eta_seconds`

| Значение | Когда                                                               |
|----------|---------------------------------------------------------------------|
| 0        | Ждать нечего, `waiting` равен нулю                                  |
| число    | Секунды на остаток при текущих лимитах                              |
| `null`   | Суммарный лимит нулевой: ни у кого нет ограничения, оценивать нечем |

Реальное время отличается: часть позиций уйдет в возврат, не потратив всех попыток, а часть
заданий вернется в очередь по бэкоффу.

## Сверка

### Описание
Расхождения разделены на два вида, и смешивать их нельзя. **Аномалии** — кто-то потерял
деньги или товар: заказ закрыт, а деньги не разнесены; позиция оплачена и висит без кода
и без возврата; контент выдан, а статус не переведен. **Наблюдения** разбираются сами —
повтором с новым ключом попытки, восстановлением зависших позиций — и в счетчик не идут,
иначе он всегда будет красным и перестанет что-либо значить.

Счетчик аномалий определяет и код ответа: `200`, если он нулевой, `409` — если нет.
Мониторингу этого достаточно, тело читать не обязательно.

### Запрос
```bash
curl -i "http://localhost:8585/api/reconciliation?stale_minutes=15" -H 'Accept: application/json'
```

### Параметры запроса

| Параметр      | Тип     | Обязателен | Описание                                                                                                                                         |
|---------------|---------|------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| stale_minutes | Integer | нет        | Окно тишины в минутах: сколько позиция или вебхук должны простоять, чтобы считаться зависшими. По умолчанию 15, допустимо от 0 до 10080 (неделя) |

Окно нужно, чтобы не поднимать тревогу над тем, что прямо сейчас обрабатывается. `0` берет
все без скидки на текущую работу — так видно и то, что еще в норме.

| Список                  | Что значит                                                                                                  | Чем разбирается                                  |

| unsettled_closed_orders | Заказ в `delivered`, `partially_delivered` или `refunded`, а `charged` не равен `delivered` плюс `refunded` | Руками: деньги уже нельзя разнести автоматически |
| paid_but_not_settled    | По позиции есть успешное списание, сама она не `delivered` и не `refunded`, и не менялась дольше окна       | `marketplace:recover-orders`                     |
| content_without_status  | Процесс умер между записью контента и переводом статуса                                                     | `marketplace:recover-orders`                     |
| rejected_refunds        | Возврат отклонен платежной системой, `failed_reason` говорит чем                                            | Руками: деньги не ушли и сами не уйдут           |
| stalled_before_finalize | Заказ в `paid` или `delivering`, все позиции завершили выдачу, а закрытия не случилось                      | Повторным закрытием, задание могло потеряться    |
| amount_mismatch         | Обработанный вебхук об оплате разошелся с заказом по сумме или валюте                                       | Руками, вместе с платежной системой              |

проводки, `stalled_before_finalize` — заказы. У `unsettled_closed_orders`, `amount_mismatch`
и `unprocessed_callbacks` состав свой, он виден в примере.

`stalled_before_finalize` ограничен двумя сотнями записей: список нужен, чтобы увидеть
проблему, а не чтобы выгрузить ее целиком. На этот предел упирается и `anomalies`.

| Список                | Что значит                                                                                      |
|-----------------------|-------------------------------------------------------------------------------------------------|
| unpaid_orders         | Заказы в `created` старше окна: похоже на потерянный вебхук. Не более 200 записей               |

аномалий не идет. Смотреть на них стоит как на динамику: рост `orphaned_vendor_codes`

# Проверка

## Заказ из нескольких товаров, где часть может не выдаться

```bash
docker compose exec app php artisan marketplace:delivery-test --orders=10 --items=3
```

Команда создает мультитоварные заказы, доводит их до конца и проверяет инварианты.
Реальный прогон:

```
оплачено вебхуком: 10 из 10
создано заказов: 10

статусы заказов                статусы позиций
  partially_delivered    4       refunded            4
  delivered              6       delivered          26

исходы попыток у поставщиков
  vendor_a   error 4   success 16   timeout 7   unverified 5
  vendor_b             success  3   timeout 1   unverified 1
  vendor_c   error 3   success  7   timeout 1   unverified 1

инварианты
  OK   выдано единиц контента = позиций delivered      26 = 26
  OK   один код не выдан дважды                         0
  OK   возвратов = позиций refunded                      4 = 4
  OK   закрытых заказов с неразнесенными деньгами        0

деньги
  оплачено 40 670.00 = выдано 35 080.00 + возвращено 5 590.00 + остаток 0.00
```

Четыре заказа в `partially_delivered` — это и есть частичный сбой: выданное осталось
у покупателя, за невыданное деньги вернулись. Позиции идут независимо, у каждой свой
поставщик и свой исход. Остаток нулевой — все заказы дошли до конца; если очередь
не успевает за отведенные раунды, команда предупреждает и остаток будет ненулевым.

### Повторяемость шагов

Закрытие заказа идемпотентно: три вызова дают ровно один возврат на позицию.

```bash
docker compose exec app php artisan marketplace:recover-orders
```

Exactly-once на оплате — двадцать пять параллельных вебхуков по одному заказу:

```bash
docker compose exec app php artisan marketplace:race-test --requests=25
```

```
HTTP-ответы: {"200":25}

  OK   все вебхуки приняты (200)        25 = 25
  OK   событий в журнале платежей       25 = 25
  OK   переходов created -> paid         1
  OK   переходов paid -> delivering      1
  OK   выданных ключей по заказу         1

exactly-once подтвержден
```

### Аварийная остановка

```bash
docker compose kill queue && docker compose up -d queue
docker compose exec app php artisan marketplace:recover-orders
```

Состояние живет в базе, а не в payload задания, поэтому повтор продолжает с того же места.
Незавершенная попытка в журнале означает «поставщик мог выдать код» — к нему идут с тем же
ключом попытки, а не к следующему.

### Как проверить, что деньги сходятся

```bash
docker compose exec app php artisan marketplace:reconcile
```

```
денежный итог
  оплачено      73 430.00
  из них выдано 33 480.00
  возвращено    38 750.00
  еще в работе   1 200.00
```

Прогон выключает автосписание и платит заказы сам, заведомо успешно: иначе исход разыгрывает
заглушка в воркере, и в выборку попадают заказы, за которые никто не платил, — инварианты
про потери и сходимость считали бы их наравне с остальными. Вебхуки уходят настоящим HTTP
на тот же адрес, куда стучалась бы заглушка, залпом — так проверяется весь путь целиком:
маршрут, валидация, журнал событий, отсечение повторов.

Инвариант — **оплачено = выдано + возвращено + еще в работе**. Он верен по построению:
лента только дополняется, отдельная проводка «выдано» не нужна, потому что выданное —
это `charge` без парного `refund`.

Настоящая проверка требования — на **завершенных** заказах: у закрытого заказа остатка быть
не может. Пока позиция в работе, ее деньги не потеряны, а просто не разнесены.

```sql
-- закрытые заказы с неразнесенными деньгами; должно быть 0 строк
SELECT o.id, t.charged, t.delivered, t.refunded
  FROM orders o JOIN LATERAL (...) t ON true
 WHERE o.status IN ('delivered','partially_delivered','refunded')
   AND abs(t.charged - t.delivered - t.refunded) > 0.005;
```

Этот же запрос — в `Order::closedWithUnsettledMoney()`, в сверке и в обеих тестовых командах.
Суммы считаются в копейках через `bcmath`, поэтому «разнесено ли все» — это сравнение с нулем,
а не допуск. Тот же ответ отдает API: `GET /api/reconciliation` возвращает `200`, когда
аномалий нет, и `409`, когда есть.

Барьеры от двойного движения денег:

| Барьер                                                             | Что запрещает                               |
|--------------------------------------------------------------------|---------------------------------------------|
| `unique(order_item_id) WHERE type='charge'`                        | второе списание по позиции                  |
| `unique(order_item_id) WHERE type='refund' AND status='succeeded'` | второй успешный возврат                     |
| стабильный ключ `refund:{item_id}` в ПС                            | второй возврат на стороне платежной системы |
| условный `UPDATE ... WHERE status = ?`                             | второй переход `created → paid`             |

Три исхода возврата различаются намеренно: успех пишет проводку и переводит позицию
в `refunded`; отказ ПС — денежный факт, попадает в ленту с `failed_reason`, но в итогах
не участвует и подбирается сверкой; недоступность ПС **не пишет ничего** и повторяется тем же
ключом, потому что неизвестно, прошел возврат или нет.

## Поставщик, которому нельзя доверять

`VendorC` умеет три вещи, которых честные не делают. Доли задаются в `.env`:

```
VENDOR_C_DUPLICATE_RATE=15      # отдает код, уже выданный другому запросу
VENDOR_C_FOREIGN_CODE_RATE=15   # отдает код из чужого пула
VENDOR_C_LYING_ERROR_RATE=20    # резервирует и выдает код, а отвечает ошибкой
VENDOR_C_ERROR_RATE=10
VENDOR_C_TIMEOUT_RATE=10
```

Со стороны вызывающего дубль и чужой код выглядят обычной успешной выдачей — поставщик
не сообщает, что врет.

У `VendorC` `priority = 2`, то есть он последний резерв. Чтобы его поведение проявлялось,
заведен SKU `GIFT-APPSTORE-1000`: `VendorSeeder` связывает его только с C, и ключи под него
есть тоже только у него. Иначе заказ тратил бы два холостых обращения к A и B — под лимитом
это прямые расходы. В прогоне выше это
строка `vendor_c foreign_code 2` — дважды чужой код был отвергнут, и заказы все равно доехали.

### Чем ловим

**Дубль** — глобальным `unique(key)` на выданных кодах. В первом этапе уникальность была
`(key, vendor)`, и этого мало: чужой код от другого поставщика проходил как новая пара.
Нарушение индекса — не авария, а штатный детектор: вставка кода идет в одной транзакции
с переводом позиции в `delivered`, и исключение означает «поставщик дал чужой код».

**Чужой код, еще никем не занятый** — верификацией. После успешной выдачи у поставщика
спрашивается, что числится за ключом этой попытки. Не назвал тот же код — код не наш.

**Вранье про ошибку** — тем, что `error` больше не означает «точно не выдал». Прежде чем уйти
к следующему поставщику, спрашиваем журнал того же: подтвердит, что код выдан — забираем его.

| Исход          | Первый этап               | Второй этап                                    |
|----------------|---------------------------|------------------------------------------------|
| `out_of_stock` | сразу к следующему        | без изменений — единственный достоверный отказ |
| `error`        | сразу к следующему        | сначала `checkKey` у того же, потом решение    |
| `timeout`      | к тому же с тем же ключом | без изменений                                  |
| успех          | принимаем                 | принимаем **после** проверки принадлежности    |

**Выход из тупика.** Если поставщик закрепил за ключом попытки негодный код, повтор с тем же
ключом вечно возвращал бы тот же мусор. Поэтому идентификаторов два: `order_items.request_id`
стабилен навсегда, а `attempt_request_id = uuid5(request_id, vendor, номер попытки)` меняется
при отклонении кода. Вычисляется, а не хранится, поэтому повтор упавшей джобы переиспользует
прежний ключ.

## Всплеск заказов и лимит поставщика

```bash
docker compose up -d queue     # прогон наблюдает за настоящим воркером, а не эмулирует его
docker compose exec app php artisan marketplace:burst-test --orders=30 --items=2 --rpm=30
```

```
оплачено вебхуком: 30 из 30
создано заказов: 30 залпом
лимит: 30 запросов в минуту на поставщика

запросы к поставщикам по минутам
  ок  vendor_a  12:39  30      ок  vendor_b  12:39  9      ок  vendor_c  12:39  30
  ок  vendor_a  12:40  30      ок  vendor_b  12:40  2      ок  vendor_c  12:40  11
  ок  vendor_a  12:41  30      ок  vendor_b  12:41  4
  ок  vendor_a  12:42  30      ок  vendor_b  12:42  2      ок  vendor_c  12:42  6
  ок  vendor_a  12:43   8

инварианты
  OK   пиковая минута не превышает лимит   30 / 30
  OK   позиций не дошло до конца            0
  OK   заданий в failed_jobs                0
  OK   закрытых заказов с неразнесенными деньгами 0

всплеск пройден: лимит соблюден, ничего не потеряно
```

Шестьдесят позиций при лимите 30 запросов в минуту разбираются за пять минут, и ни в одну
из них лимит не превышен. Прогон выключает автосписание и оплачивает заказы залпом настоящих
вебхуков — иначе часть из них разыграла бы отказ оплаты, их позиции навсегда остались бы
`pending`, и проверка «ничего не потеряно» считала бы их потерянными. Если очередь не успевает
разобраться за отведенные раунды, команда предупреждает — увеличьте `--drain-rounds`.

**Лимит.** Ключ счетчика включает календарную минуту, поэтому окно ограничения и окно проверки
это один и тот же счетчик. Настройка — `VENDOR_A_RPM` / `VENDOR_B_RPM` / `VENDOR_C_RPM`, `0`
снимает ограничение; на лету лимит меняется через кэш, без передеплоя.

Ограничение наложено **декоратором поверх процессора**, а не middleware джобы: поставщик
выбирается внутри выдачи, по статистике цикла, и на момент постановки задания неизвестен.
Заодно под лимит попадают все обращения, включая `checkKey` при проверке кода, — если считать
только выдачи, реальный расход вдвое выше заявленного.

**Ничего не теряется.** При исчерпанном лимите задание не падает, а возвращается в очередь
с задержкой до конца минуты плюс джиттер. `$tries = 0` и `retryUntil()` вместо конечного
счетчика попыток: иначе первый же возврат убил бы задание.

**Приоритет.** Выдача оплаченных заказов вынесена в отдельный супервизор Horizon со своим
пулом воркеров — подробности в разделе «Очереди». Неоплаченные заказы к поставщикам не ходят
вовсе и не отнимают у выдачи ни одного запроса из лимита.

**Прогресс** виден в `GET /api/queue/status`: сколько позиций ждет, сколько выдано, остаток
лимита по каждому поставщику, глубина очередей и грубая оценка времени на остаток.

## Восстановление картины на любой момент

Состояние на момент считается сверткой двух лент: журнал дает статусы, лента проводок —
деньги. По реальному заказу:

```
05:18:31 → paid                | pending, pending      | держим 3190
05:18:37 → delivering          | delivered, delivering | держим 3190
05:18:43 → partially_delivered | delivered, refunded   | держим 1990
```

Запрос до создания заказа отвечает «заказа не существовало на тот момент». Повторный запрос
на тот же момент дает тот же ответ — обе ленты только дополняются и отвергают `update`
и `delete` (`AppendOnlyViolationException`).

Сходимость проекции:

```bash
docker compose exec app php artisan marketplace:verify-projection
```

Свертка истории на «сейчас» обязана давать то же, что лежит в таблицах. Расхождение означает
либо смену статуса мимо `tryTransitionTo()`, либо переписанную историю.

Итоги за период считаются из той же ленты: `GET /api/reports?from=…&to=…`.

# Схема данных

| Таблица                 | Назначение                                               | Ключевые ограничения                                                                     |
|-------------------------|----------------------------------------------------------|------------------------------------------------------------------------------------------|
| `orders`                | заказ, итоговая сумма, статус                            | —                                                                                        |
| `order_items`           | позиция: свой `request_id`, статус, цикл выдачи, контент | —                                                                                        |
| `order_transactions`    | append-only лента денег                                  | `unique(order_item_id) WHERE charge`, `unique(order_item_id) WHERE refund AND succeeded` |
| `vendor_keys`           | выданные ключи                                           | **`unique(key)`**, `unique(order_item_id)`                                               |
| `vendor_gift_cards`     | выданные гифткарты                                       | `unique(code)`, `unique(order_item_id)`                                                  |
| `order_processing_logs` | append-only журнал статусов и попыток                    | `unique(parent_log_id)`, `unique(attempt_request_id, type)`                              |
| `payment_callback_logs` | входящие вебхуки                                         | `unique(ps_callback_id, payment_system)`                                                 |
| `external_vendor_keys`  | пулы заглушек                                            | `unique(vendor_name, request_id)`, `unique(key, vendor_name)`                            |

Гифткарты вынесены в отдельную модель: это другой продукт, и `IOrderContent` с `morphTo`
для того и был заложен в первом этапе. `OrderContentFactory` выбирает модель по типу товара,
спрашивая у самих моделей, что они обслуживают, и оттуда же собирает morph map.

Барьер по коду получился свой в каждой таблице контента, а не общий на все коды. Этого
достаточно: подмена кода недобросовестным поставщиком идет по тому же SKU, а SKU однозначно
задает тип товара, так что чужой код всегда оказывается в той же таблице.

# Ограничения и осознанные упрощения

**Верификация кода удваивает расход лимита запросов.** Проверка принадлежности — обязательный второй
вызов на каждую успешную выдачу. Политика единая для всех поставщиков, без флага доверия,
чтобы в повторах не заводились исключения. Если бюджет окажется тесным, первый кандидат
на сужение — включать верификацию только для недоверенных.

**Счетчик лимита может завысить на единицу.** Если процесс убит между занятием места
и компенсирующим откатом, счетчик останется выше числа реально выданных запросов.

**`verify-projection` показывает расхождения на старых заказах.** История статусов позиций
появилась во втором этапе, у заказов первого ее нет — свертка честно возвращает `unknown`.
Это не дефект механизма, а отсутствие данных до его появления.

**Старая джоба выдачи оставлена как deprecated-переходник.** `OrderKeyDeliveringAttemptJob`
не удалена: на момент выката в Redis могли лежать задания старого вида, и удаление класса
отправило бы их в `failed_jobs` с «class not found», а заказы тихо встали бы. Класс
разворачивает себя в задания по позициям и логирует `order.delivery.deprecated_job` — по нему
видно, когда очередь разобрана и класс можно убрать.

**Заглушки вызываются внутри процесса**, кроме вебхука платежной системы: он идет настоящим
HTTP на наш же эндпоинт, чтобы проверялся весь путь — маршрут, валидация, журнал событий,
отсечение повторов.

**Автотестов PHPUnit нет.** Задание их не требует, а пункты «как воспроизвести сбой»
и «как проверить деньги» закрывают артизан-команды выше.
