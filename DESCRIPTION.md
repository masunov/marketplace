# API

## Создание закакза

### Запрос
```bash
curl -X POST http://localhost:8585/api/orders \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"sku":"KEY-GTA5"}'
```

### Ответ
**HTTP 201**
```json
{
    "data": {
        "id": "01a05a5a-c88e-72b1-aea0-144ad1ec6e08",
        "status": "created",
        "price": "1990.00",
        "currency": "RUB",
        "product": {
            "sku": "KEY-GTA5",
            "name": "GTA V ключ активации",
            "type": "key"
        },
        "content": null,
        "created_at": "2026-09-01 12:24:54",
        "updated_at": "2026-09-01 12:24:54"
    }
}
```

| Поле         | Тип              | Обязателен | Описание                                                              |
|--------------|------------------|------------|-----------------------------------------------------------------------|
| id           | String (uuid v7) | да         | Идентификатор заказа                                                  |
| status       | String           | да         | Статус заказа, при успешном создании всегда "created", ожидает оплаты |
| price        | Decimal          | да         | Стоимость заказа                                                      |
| curreny      | String           | да         | Валюта                                                                |
| product.sku  | String           | да         | Артикул товара                                                        |
| product.name | String           | да         | Название товара                                                       |
| product.type | String           | да         | Тип товара                                                            |
| content      | Object           | нет        | Содержимое товара                                                     |
| created_at   | String           | да         | Метка создания заказа, формат Y-m-d H:i:s                             |
| updated_at   | String           | да         | Метка обновления заказа, формат Y-m-d H:i:s                           |

### Ошибки

**HTTP 422** при ошибках валидации
```json
{
    "message": "The selected sku is invalid.",
    "errors": {
        "sku": [
            "The selected sku is invalid."
        ]
    }
}
```

**HTTP 500** при серверных ошибках
```json
{
    "message": "Server error"
}
```

| Статус          | Финальный | Наличие содержимого | Описание                                            |

## 3. Восстановление

```bash
php artisan marketplace:recover-orders --dry-run
php artisan marketplace:recover-orders
php artisan marketplace:recover-callbacks --stale-seconds=0
```

После пополнения пула зависшие заказы доводятся до выдачи:

```
кандидатов: 3 → перезапущено: 3
статусы: {"delivered": 50}
заказов с >1 ключом: 0
```

**Вебхук раньше заказа** проверяется так: отправить вебхук на несуществующий `order_id`

# Настройка поведения заглушек

Доли исходов у поставщиков задаются в `.env` и суммируются в 100:

```
VENDOR_A_SUCCESS_RATE=60
VENDOR_A_ERROR_RATE=20
VENDOR_A_TIMEOUT_RATE=20
VENDOR_A_CLIENT_TIMEOUT=3
VENDOR_A_HANG_SECONDS=10
```

Сценарии воспроизводятся без правки кода:

| Сценарий               | Настройка                                         |
|------------------------|---------------------------------------------------|
| Поставщик A недоступен | `VENDOR_A_SUCCESS_RATE=0 VENDOR_A_ERROR_RATE=100` |
| Только таймауты у A    | `VENDOR_A_TIMEOUT_RATE=100`                       |
| Все успешно            | `VENDOR_A_ERROR_RATE=0 VENDOR_A_TIMEOUT_RATE=0`   |

Параметры повторов:

```
DELIVERY_BASE_DELAY=5          # задержка = base * номер попытки
DELIVERY_MAX_DELAY=300         # потолок
DELIVERY_JITTER=5              # разброс, чтобы не било залпом
DELIVERY_DEADLINE_MINUTES=60   # предохранитель от бесконечной цепочки
```

Бюджет попыток задается на пару «товар × поставщик» в пивоте `product2vendors.max_attempts`.

# Ключевые решения

## Exactly-once — три независимых уровня

Ни один из них не является единственной защитой:

1. **Уникальный ключ `(ps_callback_id, payment_system)`** в журнале платежей — отсекает повтор
   того же события, в том числе пришедший через сутки.
2. **Лок в кэше по `order:{id}:payment`** — быстрый путь: гасит толпу конкурентных вебхуков,
   не доводя их до БД. Атомарный `Cache::lock()->get()`.
3. **Условный `UPDATE ... WHERE status = ?`** — дальше проходит только тот,
   кто реально изменил строку (`affected rows = 1`).

Плюс физический барьер в БД: `unique(order_id)` на выданных ключах. Даже при ошибке
в логике приложения второй ключ на заказ вставить нельзя.

Лок с TTL добавлен как оптимизация, а не гарантия: TTL истекает, кэш может быть
недоступен. Источник истины — БД.

## Политика повторов следует из того, что известно

| Исход                   | Что известно           | Действие                                   |
|-------------------------|------------------------|--------------------------------------------|
| `error` (5xx)           | точно не выдал         | **сразу** к следующему поставщику          |
| `out_of_stock`          | точно не выдал         | **сразу** к следующему поставщику          |
| `timeout` / `in_flight` | неизвестно, мог выдать | повтор **к тому же** с тем же `request_id` |

Ключевое: после таймаута мы **никогда не уходим на другого поставщика**. Риск сжечь код у первого: он мог его уже выдать, просто ответ не дошел.

`max_attempts` в пивоте `product2vendors` — это бюджет **таймаутных** повторов, а не общий
бюджет неудач. Когда он исчерпан, заказ уходит в `delivery_failed` с причиной
`timeouts_unresolved`: разрешить неопределенность автоматически нельзя, нужен либо приход
поставщика в себя, либо ручное решение.

## Таймаут ≠ отказ

`request_id` детерминирован, живет на заказе и **никогда не перегенерируется** — ни при повторе,
ни при переходе на другого поставщика. Заглушка обязана вернуть на тот же `request_id` тот же
код, что обеспечено уникальным ключом `(vendor_name, request_id)` в ее пуле.

Заглушка резервирует ключ **до** того, как решит зависнуть. Поэтому таймаут действительно
означает «код мог быть уже выдан», а не «ничего не произошло».

Попытка пишется в журнал со статусом `in_flight` **до** обращения к поставщику и обновляется
результатом после. Если процесс умер между этими точками, следующая попытка видит `in_flight`
и трактует его как таймаут — идет к тому же поставщику с тем же `request_id`.

## Цикл доставки

Переход в `delivering` открывает новый цикл (`orders.delivery_cycle_started_at`), проставляемый
атомарно тем же условным апдейтом. Попытки считаются в рамках цикла, поэтому восстановление
из `out_of_stock` и `delivery_failed` получает полный бюджет заново, а `request_id` при этом
остается прежним — задвоения не возникает.

Маркер синхронный, а не выведенный из журнала статусов: журнал асинхронный и под нагрузкой
отстает.

## Поставщики: клиент + процессор

Клиент повторяет форму конкретного поставщика — свои DTO, свои исключения. Процессор-адаптер
приводит их к общему `VendorIssueResult` с четырьмя исходами: `success`, `timeout`, `error`,
`out_of_stock`. Джоба работает только с общим контрактом и не знает про вендорную специфику.

Ретраи, порядок обхода и бюджеты попыток живут в джобе, а не в процессорах — иначе логика
повторов размножилась бы по поставщикам.

## Самоуправляемый ретрай

`$tries = 1`, штатные неуспехи не бросают исключений — джоба сама диспатчит следующую попытку
с возрастающей задержкой. Состояние попыток лежит в БД, а не в payload задания, поэтому
видно в сверке и переживает перезапуск очереди.

## Полиморфный контент заказа

Заказ ссылается на выданный контент через `morphTo`, тип пишется алиасом (`vendor_key`),
а не именем класса. Контент другой формы (реквизиты аккаунта, промокод) добавляется новой
моделью с интерфейсом `IOrderContent` — текущий API и джоба не меняются, могут дополняться новые джобы, если флоу получения контента у поставщика другой.

## Схема данных

| Таблица                                  | Назначение                                          | Ключевые ограничения                                            |
|------------------------------------------|-----------------------------------------------------|-----------------------------------------------------------------|
| `orders`                                 | заказы, статус, цикл доставки, указатель на контент | —                                                               |
| `products`, `vendors`, `product2vendors` | каталог, поставщики, приоритет и бюджет попыток     | PK `(product_id, vendor_id)`                                    |
| `payment_callback_logs`                  | все входящие вебхуки с сырым payload                | **unique `(ps_callback_id, payment_system)`**                   |
| `vendor_keys`                            | выданные заказам ключи                              | **unique `order_id`**, unique `(key, vendor)`                   |
| `order_processing_logs`                  | смены статусов и попытки выдачи                     | индекс `(order_id, triggered_at)`                               |
| `external_vendor_keys`                   | пулы заглушек-поставщиков                           | unique `(vendor_name, request_id)`, unique `(key, vendor_name)` |

Статусы: `created → paid → delivering → delivered`, ветки `payment_failed`, `out_of_stock`,
`delivery_failed` (две последние восстановимы).

## Витрина остатков

Сейчас каталог это табличка products, в нее можно денормализовать остатки в поле `available_count` и добавил индекс
```sql
CREATE INDEX products_showcase_idx ON products (type, price, id) WHERE available_count > 0;
```
Счетчик списываем при каждой успешной выдаче, а пополняем, когда заводим позиции.

Для какиъ-нибудь дашбордов, где не критично отставание от реальных данных и есть сложные агрегации, можно построить Materialized View и обновлять cron задачей.

Дальше при росте:

- Отдельные очереди под выдачу и под логирование статусов, разные приоритеты в Horizon.
- Партиционирование `payment_callback_logs` и `order_processing_logs` по месяцам:
  растут быстрее всех, читаются почти всегда за свежий период.
- Реплика под сверку и витрину, чтобы аналитические запросы не конкурировали с выдачей.

## Ограничения

Осознанные упрощения, о которых стоит знать:

- **Products**. В задании есть фраза "Пул тестовых ключей для автоматической выдачи", в тестовых продуктах так же есть позиции с `type=key`, принято решение, что для тестирования заказов нужно использовать только SKU `KEY-CS2-PRIME` `KEY-GTA5` `KEY-EFT` с типом `key`, все остальные уйдут в `out_of_stock` после вебхука. 
- **Заглушки поставщиков вызываются внутри процесса**, а не по HTTP. Состояние фиксируется
  в БД до «зависания», поэтому ловушка таймаута воспроизводится честно, но самого сетевого
  таймаута нет — `TimeoutException` синтетический.
- **Подпись вебхука не проверяется** — по условию задания.
- **Расхождение суммы**: заказ не переводится в `paid`, пишется `Log::error`, событие
  помечается обработанным. В ТЗ этот случай не описан, решение принято самостоятельно.
- **Тест на гонки — артизан-команда, а не PHPUnit.** `RefreshDatabase` оборачивает тест
  в транзакцию, а PHPUnit однопоточен: воспроизвести гонки в такой среде невозможно. В PHPunit тесты на API добавлены не были.
- **Модели как репозитории.** Для упрощения и ускорения, но все же для соблюдения порядка, принято решение использовать модели как репозитории и всю работу приложения с базой выносить туда, статическими методами. Исключение — тесты, когда нужно выполнить какие-то частные операции.
